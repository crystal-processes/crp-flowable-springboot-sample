# JPA to Services Process Instance Migration

This document describes the automated migration feature added in version 0.3.1 that migrates process instances from JPA-based variable storage to service-based variable storage.

## Overview

**Version 0.3.0** used **JPA variables** where process instances stored direct references to JPA entities (e.g., `ContractEntity`).

**Version 0.3.1** uses **service-based variables** where process instances store only an `insuranceEventId` reference and access all data through the `insuranceEventService`.

The migration process `A001-migration.bpmn` automatically handles the transition between these two architectures on application startup.

## Process Architecture Comparison

### Version 0.3.0: JPA Variables

The process definition `P003-jpaProcessInsuranceEvent.bpmn` stored JPA entity references directly:
- `contract` variable referenced a `ContractEntity`
- Service tasks accessed entity properties directly
- Variable versioning was tied to entity structure

### Version 0.3.1: Service-based Variables

The process definition `P030-processInsuranceEvent.bpmn` uses service calls:
- `insuranceEventId` variable references the insurance event
- All data access goes through `insuranceEventService`
- Variables are isolated from entity structure changes

## The Migration Process

The `A001-migration.bpmn` process performs automated migration on application startup:

```
┌─────────────┐    ┌─────────────────┐    ┌─────────────────┐    ┌─────────────┐
│ Timer Start  │───▶│ Get Model Version│───▶│Migration Script │───▶│Set Model Version│
└─────────────┘    └─────────────────┘    └─────────────────┘    └─────────────┘
```

### Migration Steps

1. **Get Model Version** - Retrieves the current `acme.model.version` property from the database
2. **Run Migration Script 0.3.0 → 0.3.1** - If version is 0.3.0, performs the migration:
   - Finds the latest process definition (P030-processInsuranceEvent)
   - Finds the previous process definition (P003-jpaProcessInsuranceEvent)
   - Uses `ProcessMigrationService` to migrate all instances
   - Transforms variables from old format to new format
3. **Set Model Version** - Updates `acme.model.version` to 0.3.1 and removes the temporary variable

### Variable Transformation

The migration script performs these transformations:

**From (0.3.0):**
- `contractId` - String
- `eventDescription` - String  
- `amount` - Number

**To (0.3.1):**
- `insuranceEventId` - Long (generated by `insuranceEventService.createInstance()`)
- Old variables (`contractId`, `eventDescription`, `amount`) are removed

The transformation is performed via a post-upgrade Groovy script:

```groovy
import org.flowable.engine.impl.util.CommandContextUtil

println 'Migrating process instances to version 0.3.1'

def contractId = execution.getVariable('contractId')
def eventDescription = execution.getVariable('eventDescription')
def requestedAmount = execution.getVariable('amount')
def insuranceEventId = insuranceEventService.createInstance(contractId, eventDescription, requestedAmount)
execution.setVariable('insuranceEventId', insuranceEventId)

// Remove old variables
CommandContextUtil.getProcessEngineConfiguration().getRuntimeService().removeVariable(execution.getId(), 'contractId')
CommandContextUtil.getProcessEngineConfiguration().getRuntimeService().removeVariable(execution.getId(), 'eventDescription')
CommandContextUtil.getProcessEngineConfiguration().getRuntimeService().removeVariable(execution.getId(), 'amount')
```

## Testing the Migration

The companion test project **[crp-sample-upgrade-test](https://github.com/crystal-processes/crp-sample-upgrade-test)** validates the migration between versions 0.3.0 and 0.3.1.

### Test Execution

The migration test is defined in the bash script:

```bash
# run_test-phase3.sh
./mvnw --projects release-0.3.0 clean test -Dspring.profiles.active=generateData
./mvnw --projects release-0.3.1 clean test
```

This performs:
1. Generate test data with version 0.3.0
2. Run tests with version 0.3.1 to verify migration works correctly

### Local Testing

The migration process itself is tested in `MigrationProcessTest.java`:

```java
@Test
void migrationExecutesOnApplicationStart(ProcessEngineConfiguration configuration, HistoryService historyService) {
    JobTestHelper.waitForJobExecutorOnCondition(
            configuration, 10_000, 200,
            () -> historyService.createHistoricProcessInstanceQuery()
                   .processDefinitionKey("A001-migration").count() == 1);

    HistoricProcessInstance latestMigrationProcess = historyService.createHistoricProcessInstanceQuery()
            .processDefinitionKey("A001-migration").singleResult();

    assertThat(latestMigrationProcess).isFinished();
    assertThat(configuration.getManagementService().getProperties())
            .containsEntry("acme.model.version", "0.3.1");
}
```

## Key Technical Details

### Process Migration Service

The migration uses Flowable's built-in `ProcessMigrationService`:

```java
processMigrationService.createProcessInstanceMigrationBuilder()
    .migrateToProcessDefinition(latestProcessDefinition.id)
    .postUpgradeScript(new Script('groovy', migrationScript))
    .migrateProcessInstances(previousProcessDefinition.id)
```

### Version Tracking

The migration tracks the model version in a database property:
- Property key: `acme.model.version`
- Initial value: `initial` (first run)
- After migration: `0.3.1`

This ensures the migration runs only once per version.

### Process Definition Keys

- Migration process: `A001-migration`
- Old process (JPA): `P003-jpaProcessInsuranceEvent`
- New process (services): `P030-processInsuranceEvent`

## Why This Migration Matters

This migration demonstrates a critical pattern for production Flowable applications:

1. **Architecture Evolution** - Applications need to evolve from JPA direct access to service-based access
2. **Automated Upgrades** - Manual migration of process instances is error-prone; automation is essential
3. **Data Consistency** - The migration ensures all running process instances work with the new architecture
4. **Zero Downtime** - The migration runs automatically on application startup

This approach follows the [Variable Best Practices](../02_variables/04_onlyGoodVariable.md), specifically:
- **Store application data outside the process** - Using `insuranceEventId` instead of direct entity references
- **Access data through services** - All data access goes through `insuranceEventService`

## Migration Limitations

- Only migrates running process instances (completed instances remain in history)
- Requires the old process definition to still be deployed
- The migration script must handle all variable transformations
- Process must be designed with migration in mind (version tracking property)
- **Migration migrates process instance data only** – Entity migration (JPA schema changes) is out of this example's scope and must be handled separately via your database migration tool (e.g., Liquibase, Flyway)
